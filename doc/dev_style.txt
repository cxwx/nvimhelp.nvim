Nvim 代码风格指南                                        *dev-style*

为 Nvim 源代码工作的开发者的代码风格指南。

许可证：CC-By 3.0 https://creativecommons.org/licenses/by/3.0/

                                      输入 |gO| 查看目录。

==============================================================================
背景

我们保持代码库可管理的方式之一是强制一致性。任何程序员都能快速
看懂他人的代码，这一点非常重要。

保持统一的风格并遵循约定意味着我们可以更容易地使用"模式匹配"来
推断各种符号是什么以及关于它们的不变量是什么。创建通用的、必需
的惯用写法和模式使代码更容易理解。

在某些情况下，可能有充分的理由来更改某些风格规则，但我们仍然
保持原样以维护一致性。


==============================================================================
头文件                                            *dev-style-header*


头文件保护 ~

所有头文件应以 `#pragma once` 开头以防止多次包含。

    在 foo/bar.h 中：
>c
        #pragma once
<

头文件系统 ~

Nvim 使用两种类型的头文件。有"普通"头文件和 "defs" 头文件。
通常，每个普通头文件都有一个对应的 defs 头文件，例如
`fileio.h` 和 `fileio_defs.h`。这种区分是为了最小化修改时的
重新编译。原因是添加函数或修改函数签名比更改类型更频繁。
目标是实现以下几点：

- 所有头文件（defs 和普通）必须只包含 defs 头文件、系统头文件
  和生成的声明。换言之，头文件不得包含普通头文件。

- 源（.c）文件可以包含所有头文件，但只有在需要符号而非类型时
  才应包含普通头文件。

使用以下指南来确定放置内容的位置：

符号：
  - 常规函数声明
  - `extern` 变量（包括 `EXTERN` 宏）

非符号：
  - 宏，即 `#define`
  - 带有 `FUNC_ATTR_ALWAYS_INLINE` 属性的 static inline 函数
  - typedef
  - 结构体
  - 枚举

- 所有符号必须移至普通头文件。

- 被多个头文件使用的非符号应移至 defs 头文件。这是为了确保头文件
  只包含 defs 头文件。相反，只被单个头文件使用的非符号应移至
  该头文件。

- 例外：如果宏调用了函数，则必须移至普通头文件。

作用域                                                 *dev-style-scope*

局部变量 ~

将函数的变量放在尽可能窄的作用域中，并在声明时初始化变量。

C99 允许你在函数中的任何位置声明变量。在尽可能局部的作用域中
声明它们，并尽可能靠近第一次使用的位置。这使得读者更容易找到
声明并查看变量的类型和初始值。特别是，应使用初始化而不是声明后
再赋值，例如 >c

    int i;
    i = f();      // ❌：初始化与声明分离。

    int j = g();  // ✅：声明时初始化。


初始化 ~

如果没有初始化，多个声明可以定义在一行中，但每个初始化应在
单独的行上完成。

>c
    int i;
    int j;              // ✅
    int i, j;           // ✅：多个声明，无初始化。
    int i = 0;
    int j = 0;          // ✅：每行一个初始化。

    int i = 0, j;       // ❌：带初始化的多个声明。
    int i = 0, j = 0;   // ❌：带初始化的多个声明。

Nvim 专有规则

clint ~

使用 `clint.lua` 检测风格错误。

`src/clint.lua` 是一个 Lua 脚本，它读取源文件并识别风格错误。
它并不完美，既有误报也有漏报，但它仍然是一个有价值的工具。
误报可以通过在行尾添加 `// NOLINT` 来忽略。

uncrustify ~

src/uncrustify.cfg 是预期代码格式的权威文件，适用于 clint.lua
未覆盖的情况。如果 uncrustify 规则已覆盖，我们会移除 clint.lua
中的检查。

==============================================================================
其他 C 特性                                        *dev-style-features*


变长数组和 alloca() ~

我们不允许使用变长数组或 `alloca()`。

变长数组可能导致难以检测的栈溢出。


后缀递增和后缀递减 ~

在语句中使用后缀形式（`i++`）。 >c

    for (int i = 0; i < 3; i++) { }
    int j = ++i;  // ✅：++i 用作表达式。

    for (int i = 0; i < 3; ++i) { }
    ++i;  // ❌：++i 用作语句。


const 的使用 ~

尽可能使用 `const` 指针。避免在非指针参数定义上使用 `const`。

    const 的放置位置 ~

    有些人偏好 `int const *foo` 的形式而非 `const int *foo`。
    他们认为这更具可读性，因为更一致：它保持了 `const` 总是
    跟在其描述对象之后的规则。然而，在很少有深层嵌套指针
    表达式的代码库中，这种一致性论点并不适用，因为大多数
    `const` 表达式只有一个 `const`，且它应用于底层值。在这种
    情况下，没有一致性需要维护。将 `const` 放在前面可以说更
    具可读性，因为它遵循英语的习惯，将"形容词"（`const`）
    放在"名词"（`int`）之前。

    也就是说，虽然我们鼓励将 `const` 放在前面，但我们不要求
    这样做。但要与周围的代码保持一致！ >c

    void foo(const char *p, int i);
    }

    int foo(const int a, const bool b) {
    }

    int foo(int *const p) {
    }


整数类型 ~

在内置整数类型中，只使用 `char`、`int`、`uint8_t`、`int8_t`、
`uint16_t`、`int16_t`、`uint32_t`、`int32_t`、`uint64_t`、
`int64_t`、`uintmax_t`、`intmax_t`、`size_t`、`ssize_t`、
`uintptr_t`、`intptr_t` 和 `ptrdiff_t`。

仅将 `int` 用于错误码和局部的、简单的变量。

转换整数类型时要小心。整数转换和提升可能导致非直观的行为。
注意 `char` 的有符号性是由实现定义的。

面向公共的类型必须具有固定宽度（`uint8_t` 等）

固定宽度类型没有便捷的 `printf` 格式占位符。如果需要格式化
固定宽度整数，请转换为 `uintmax_t` 或 `intmax_t`。

类型		无符号	    有符号
`char`		`%hhu`	    `%hhd`
`int`		n/a	    `%d`
`(u)intmax_t`	`%ju`	    `%jd`
`(s)size_t`	`%zu`	    `%zd`
`ptrdiff_t`	`%tu`	    `%td`


布尔值 ~

使用 `bool` 表示布尔值。 >c

    int loaded = 1;  // ❌：loaded 应为 bool 类型。


条件表达式 ~

不要使用 "yoda 条件"。每个条件最多使用一个赋值。 >c

    if (1 == x) {

    if (x == 1) {  // 使用此顺序

    if ((x = f()) && (y = g())) {


函数声明 ~

每个函数不得有单独的声明。

函数声明由 gen_declarations.lua 脚本创建。 >c

    static void f(void);

    static void f(void)
    {
      ...
    }


通用翻译单元布局 ~

公共函数的定义位于静态函数定义之前。 >c

    <HEADER>

    <PUBLIC FUNCTION DEFINITIONS>

    <STATIC FUNCTION DEFINITIONS>


与声明生成器的集成 ~

每个 C 文件必须包含生成头文件的 #include。

#include 必须在 .c 文件中的其他 #include 和 typedef 之后，在
头文件中则在其他所有内容之后。如果 .c 文件不包含任何静态函数，
则允许省略 .c 文件中的 #include。

包含的文件名由 .c 文件名（不含扩展名）组成，前面加上相对于
src/nvim 的目录名。包含静态函数声明的文件名以
`.c.generated.h` 结尾，`*.h.generated.h` 文件仅包含非静态
函数声明。 >c

    // src/nvim/foo.c 文件
    #include <stddef.h>

    typedef int FooType;

    #include "foo.c.generated.h"

    …


    // src/nvim/foo.h 文件
    #pragma once

    …

    #include "foo.h.generated.h"


64 位可移植性 ~

代码应同时兼容 64 位和 32 位。注意打印、比较和结构体对齐的
问题。

- 记住 `sizeof(void *)` != `sizeof(int)`。如果你想要指针大小的
  整数，请使用 `intptr_t`。

- 你可能需要注意结构体对齐，特别是存储在磁盘上的结构体。任何
  包含 `int64_t`/`uint64_t` 成员的类/结构体在 64 位系统上默认
  会 8 字节对齐。如果你有这样的结构体在 32 位和 64 位代码之间
  的磁盘上共享，你需要确保它们在两种架构上以相同方式打包。
  大多数编译器提供了修改结构体对齐的方法。对于 gcc，你可以使用
  `__attribute__((packed))`。MSVC 提供了 `#pragma pack()` 和
  `__declspec(align())`。

- 根据需要使用 `LL` 或 `ULL` 后缀来创建 64 位常量。例如： >c

    int64_t my_value = 0x123456789LL;
    uint64_t my_mask = 3ULL << 48;


sizeof ~

优先使用 `sizeof(varname)` 而非 `sizeof(type)`。

当获取特定变量的大小时，使用 `sizeof(varname)`。
`sizeof(varname)` 会在有人现在或以后更改变量类型时适当更新。
你可以对与任何特定变量无关的代码使用 `sizeof(type)`，例如管理
外部或内部数据格式的代码，其中适当的 C 类型变量不方便使用。 >c

    Struct data;
    memset(&data, 0, sizeof(data));

    memset(&data, 0, sizeof(Struct));

    if (raw_size < sizeof(int)) {
      fprintf(stderr, "compressed record not big enough for count: %ju", raw_size);
      return false;
    }

命名                                                  *dev-style-naming*

最重要的一致性规则是那些管理命名的规则。名称的风格立即告诉我们
被命名实体是什么类型的东西：类型、变量、函数、常量、宏等，而不
需要我们搜索该实体的声明。我们大脑中的模式匹配引擎在很大程度上
依赖于这些命名规则。

命名规则相当随意，但我们认为在这个领域一致性比个人偏好更重要，
因此无论你觉得这些规则是否合理，规则就是规则。


通用命名规则 ~

函数名、变量名和文件名应具有描述性；避免缩写。

在合理范围内给出尽可能描述性的名称。不要担心节省水平空间，因为
让你的代码能被新读者立即理解要重要得多。不要使用对项目外读者
模棱两可或不熟悉的缩写，也不要通过删除单词中的字母来缩写。 >c

    int price_count_reader;    // 无缩写。
    int num_errors;            // "num" 是一种广泛的约定。
    int num_dns_connections;   // 大多数人知道 "DNS" 代表什么。

    int n;                     // 无意义。
    int nerr;                  // 模糊的缩写。
    int n_comp_conns;          // 模糊的缩写。
    int wgc_connections;       // 只有你的团队知道这代表什么。
    int pc_reader;             // 很多东西可以缩写为 "pc"。
    int cstmr_id;              // 删除了内部字母。


文件名 ~

文件名应全部小写，可以包含下划线（`_`）。

使用下划线分隔单词。可接受的文件名示例： >

    my_useful_file.c
    getline_fix.c  // ✅：getline 指的是 glibc 函数。

C 文件应以 `.c` 结尾，头文件应以 `.h` 结尾。

不要使用 `/usr/include` 中已存在的文件名，如 `db.h`。

一般来说，让你的文件名非常具体。例如，使用 `http_server_logs.h`
而非 `logs.h`。


类型名 ~

typedef 的结构体和枚举以大写字母开头，每个新单词有一个大写字母，
不使用下划线：`MyExcitingStruct`。

非 typedef 的结构体和枚举全部小写，单词之间用下划线分隔：
`struct my_exciting_struct`。 >c

    struct my_struct {
      ...
    };
    typedef struct my_struct MyAwesomeStruct;


变量名 ~

变量名全部小写，单词之间用下划线。例如：
`my_exciting_local_variable`。

    常见变量名 ~

    例如： >c

        string table_name;  // ✅：使用下划线。
        string tablename;   // ✅：全部小写。

        string tableName;   // ❌：混合大小写。
<

    结构体变量 ~

    结构体中的数据成员应像普通变量一样命名。 >c

        struct url_table_properties {
          string name;
          int num_entries;
        }
<

    全局变量 ~

    除非绝对必要，否则不要使用全局变量。全局变量以 `g_` 为前缀。


常量名 ~

使用 `k` 后跟混合大小写：`kDaysInAWeek`。

所有编译时常量，无论是局部声明还是全局声明，都遵循与其他变量
略有不同的命名约定。使用 `k` 后跟首字母大写的单词： >c

    const int kDaysInAWeek = 7;

函数名 ~

函数名全部小写，单词之间用下划线。例如：
`my_exceptional_function()`。同一头文件中的所有函数应有一个
公共前缀。

在 `os_unix.h` 中： >c

    void unix_open(const char *path);
    void unix_user_id(void);

如果你的函数在出错时崩溃，你应该在函数名后附加 `or_die`。
这仅适用于可能被生产代码使用的函数以及在正常操作期间合理
可能发生的错误。


枚举器名 ~

枚举器应像常量一样命名：`kEnumName`。 >c

    enum url_table_errors {
      kOK = 0,
      kErrorOutOfMemory,
      kErrorMalformedInput,
    };


宏名 ~

它们是这样的：`MY_MACRO_THAT_SCARES_CPP_DEVELOPERS`。 >c

    #define ROUND(x) ...
    #define PI_ROUNDED 5.0


==============================================================================
注释                                                *dev-style-comments*

注释对于保持代码可读性至关重要。以下规则描述了你应该在什么地方
注释什么。但记住：虽然注释非常重要，但最好的代码是自文档化的。

编写注释时，为你的读者写：下一个需要理解你代码的贡献者。要
慷慨 -- 下一个可能就是你！

Nvim 使用 Doxygen 注释。


注释风格 ~

只使用 `//` 风格的语法。 >c

    // 这是一个跨越
    // 多行的注释
    f();


文件注释 ~

每个文件以其内容的描述开头。

    法律声明 ~

    我们没有这类东西。这些东西在 LICENSE 中，并且只在那里。

    文件内容 ~

    每个文件应在顶部有一个描述其内容的注释。

    通常 `.h` 文件会描述在文件中声明的变量和函数，概述它们的
    用途和使用方式。`.c` 文件应包含更多关于实现细节或棘手算法
    的讨论。如果你觉得实现细节或算法讨论对阅读 `.h` 的人有用，
    可以放在那里，但在 `.c` 中注明文档在 `.h` 文件中。

    不要在 `.h` 和 `.c` 中都写重复的注释。重复的注释会产生
    分歧。 >c

    /// 此文件的简要描述。
    ///
    /// 此文件的更长描述。
    /// 在此处要非常慷慨。


结构体注释 ~

每个结构体定义应有附带的注释，描述它的用途和如何使用。 >c

    /// 与缓冲区一起存储的窗口信息。
    ///
    /// 为缓冲区保存两种类型的信息，这些信息与特定窗口关联：
    /// 1. 每个窗口可以有一个与缓冲区关联的不同行号。
    /// 2. 缓冲区的窗口局部选项以类似方式工作。
    /// 窗口信息保存在 g_wininfo 的列表中。按最近使用的顺序
    /// 保存。
    struct win_info {
      /// 下一个条目或最后条目的 NULL。
      WinInfo *wi_next;
      /// 前一个条目或第一个条目的 NULL。
      WinInfo *wi_prev;
      /// 指向执行 wi_fpos 的窗口的指针。
      Win *wi_win;
      ...
    };

如果字段注释很短，你也可以将它们放在字段旁边。但在一个结构体
内要保持一致，并遵循必要的 doxygen 风格。 >c

    struct wininfo_S {
      WinInfo *wi_next;  ///< 下一个条目或最后条目的 NULL。
      WinInfo *wi_prev;  ///< 前一个条目或第一个条目的 NULL。
      Win *wi_win;       ///< 指向执行 wi_fpos 的窗口的指针。
      ...
    };

如果你已经在文件顶部的注释中详细描述了一个结构体，可以简单地
说明"参见文件顶部的注释以获取完整描述"，但确保有某种注释。

记录结构体所做的同步假设（如果有的话）。如果结构体的实例可以被
多个线程访问，请特别注意记录围绕多线程使用的规则和不变量。


函数注释 ~

声明处的注释描述函数的使用；定义处的注释描述函数的操作。

    函数声明 ~

    每个函数声明应紧接在其前面有注释，描述函数的功能和使用方法。
    这些注释应是描述性的（"打开文件"）而非命令式的（"打开文件"）；
    注释描述函数，它不是告诉函数要做什么。一般来说，这些注释不
    描述函数如何执行其任务。相反，这应留给函数定义中的注释。

    在函数声明注释中要提及的内容类型：

    - 如果函数分配了调用者必须释放的内存。
    - 任何参数是否可以是空指针。
    - 如果函数的使用方式有任何性能影响。
    - 如果函数是可重入的。它的同步假设是什么？ >c
    /// 函数的简要描述。
    ///
    /// 详细描述。
    /// 可以跨越多个段落。
    ///
    /// @param arg1 arg1 的描述
    /// @param arg2 arg2 的描述。可以跨越
    ///        多行。
    ///
    /// @return 返回值的描述。
    Iterator *get_iterator(void *arg1, void *arg2);
<

    函数定义 ~

    如果函数执行任务的方式有任何技巧，函数定义应有一个解释性
    注释。例如，在定义注释中你可能描述你使用的任何编码技巧，
    概述你经历的步骤，或解释为什么你选择以这种方式实现函数而
    不是使用可行的替代方案。例如，你可能提到为什么它必须在函数
    的前半部分获取锁，但后半部分不需要。

    注意你不应该只是重复函数声明中给出的注释（在 `.h` 文件或
    其他地方）。简要概括函数做什么是可以的，但注释的重点应在
    于它是如何做到的。 >c

    // 注意这里我们不使用 Doxygen 注释。
    Iterator *get_iterator(void *arg1, void *arg2)
    {
      ...
    }


变量注释 ~

一般来说，变量的实际名称应该足够描述性，能很好地说明变量的
用途。在某些情况下，需要更多注释。

    全局变量 ~

    所有全局变量应有注释描述它们是什么以及用途。例如： >c

        /// 我们在此回归测试中运行的测试用例总数。
        const int kNumTestCases = 6;


实现注释 ~

在你的实现中，你应该在代码的棘手、不明显、有趣或重要的部分
添加注释。

    行注释 ~

    此外，不明显的行应在行尾添加注释。这些行尾注释应与代码
    隔开 2 个空格。示例： >c

        // 如果我们有足够的内存，也 mmap 数据部分。
        mmap_budget = max<int64>(0, mmap_budget - index_->length());
        if (mmap_budget >= data_size_ && !MmapData(mmap_chunk_bytes, mlock)) {
          return;  // 错误已记录。
        }
<
    注意既有描述代码做什么的注释，也有提到当函数返回时错误
    已经被记录的注释。

    如果在连续行上有多个注释，通常将它们对齐会更具可读性： >c

        do_something();                      // 此处的注释使注释对齐。
        do_something_else_that_is_longer();  // 此处的注释使代码和注释
                                             // 之间有两个空格。
        { // 打开新作用域时注释前一个空格是允许的，
          // 这样注释与后面的注释和代码对齐。
          do_something_else();  // 行注释前通常两个空格。
        }
<

    NULL、true/false、1、2、3... ~

    当你传入空指针、布尔值或字面整数值给函数时，你应该考虑
    添加注释说明它们是什么，或通过使用常量使代码自文档化。
    例如，比较： >c

        bool success = calculate_something(interesting_value,
                                           10,
                                           false,
                                           NULL);  // 这些参数是什么？？
<

    与： >c

        bool success = calculate_something(interesting_value,
                                           10,     // 默认基值。
                                           false,  // 不是第一次调用。
                                           NULL);  // 无回调。
<

    或者，使用常量或自描述变量： >c

        const int kDefaultBaseValue = 10;
        const bool kFirstTimeCalling = false;
        Callback *null_callback = NULL;
        bool success = calculate_something(interesting_value,
                                           kDefaultBaseValue,
                                           kFirstTimeCalling,
                                           null_callback);
<

    不要做 ~

    注意你永远不应该描述代码本身。假设阅读代码的人比你更了解
    C，即使他或她不知道你想做什么： >c

        // 现在遍历 b 数组并确保如果 i 出现，
        // 下一个元素是 i+1。
        ...        // 天哪。多么无用的注释。


标点、拼写和语法 ~

注意标点、拼写和语法；阅读写得好的注释比写得差的要容易。

注释应像叙述文本一样可读，有正确的大写和标点。在许多情况下，
完整句子比句子片段更可读。较短的注释，如代码行末尾的注释，
有时可以不太正式，但你应该与你的风格保持一致。

虽然代码审查者指出你应该使用分号而不是逗号可能令人沮丧，但
源代码保持高水平的清晰度和可读性非常重要。正确的标点、拼写
和语法有助于实现这一目标。


TODO 注释 ~

对临时的、短期解决方案的或足够好但不完美的代码使用 `TODO`
注释。

`TODO` 应包含全大写的 `TODO` 字符串，后跟能最好地提供由
`TODO` 引用的问题上下文的人的姓名、电子邮件地址或其他标识符。
主要目的是有一个一致的 `TODO` 格式，可以搜索以找到能在请求时
提供更多详细信息的人。`TODO` 不是被引用人会修复问题的承诺。
因此，当你创建 `TODO` 时，几乎总是你自己的名字。 >c

    // TODO(kl@gmail.com): Use a "*" here for concatenation operator.
    // TODO(Zeke): change this to use relations.

如果你的 `TODO` 是"在将来某个日期做某事"的形式，请确保你包含
一个非常具体的日期（"在 2005 年 11 月前修复"）或一个非常具体
的事件（"当所有客户端都能处理 XML 响应时移除此代码。"）。


弃用注释 ~

用 `@deprecated` 文档字符串标记标记弃用的接口点。

你可以通过编写包含全大写 `@deprecated` 的注释来标记接口为弃用。
注释放在接口声明之前或声明的同一行。

在 `@deprecated` 之后，在括号中写上你的姓名、电子邮件或其他
标识符。

弃用注释必须包含简单、清晰的指示，让人们修复其调用点。在 C 中，
你可以将弃用函数实现为调用新接口点的内联函数。

将接口点标记为 `DEPRECATED` 不会神奇地导致任何调用点更改。如果
你想让人们真正停止使用弃用的功能，你必须自己修复调用点或招募
一个团队来帮助你。

新代码不应包含对弃用接口点的调用。请改用新接口点。如果你不
理解指示，请找到创建弃用的人并请他们帮助你使用新接口点。

格式化                                              *dev-style-format*

编码风格和格式化相当随意，但如果每个人都使用相同的风格，项目就
更容易遵循。个人可能不同意格式化规则的每个方面，有些规则可能需
要一些时间来适应，但重要的是所有项目贡献者遵循风格规则，这样他
们都可以轻松地阅读和理解每个人的代码。


非 ASCII 字符 ~

非 ASCII 字符应该很少出现，且必须使用 UTF-8 格式。

你不应该在源代码中硬编码面向用户的文本（或者你应该？），即使是
英文，所以非 ASCII 字符的使用应该很少。然而，在某些情况下，在
代码中包含这些词是合适的。例如，如果你的代码解析来自外部来源的
数据文件，可能适合将这些数据文件中用作分隔符的非 ASCII 字符串
硬编码。更常见的是，不需要本地化的单元测试代码可能包含非 ASCII
字符串。在这种情况下，你应该使用 UTF-8，因为这是大多数能处理
ASCII 以上内容的工具都理解的编码。

十六进制编码也可以，并且在增强可读性时是推荐的 -- 例如，
`"\uFEFF"` 是 Unicode 零宽无间断空格字符，如果在源代码中直接
包含 UTF-8 则将不可见。


大括号初始化列表 ~

格式化大括号列表与你在其位置格式化函数调用完全相同，但在 `{`
之后和 `}` 之前各有一个空格。

如果大括号列表跟在名称（例如类型或变量名）之后，格式化时将
`{}` 视为与该名称的函数调用的括号。如果没有名称，假设一个
零长度名称。 >c

    struct my_struct m = {  // 在此处，你也可以在 { 之前换行。
        superlongvariablename1,
        superlongvariablename2,
        { short, interior, list },
        { interiorwrappinglist,
          interiorwrappinglist2 } };


循环和 Switch 语句 ~

注释非平凡的 fall-through。

如果不是基于枚举值的条件，switch 语句应始终有 `default` 情况
（在枚举值的情况下，编译器会在你没有处理所有值时发出警告）。
如果默认情况永远不应执行，只需使用 `abort()`： >c

    switch (var) {
      case 0:
        ...
        break;
      case 1:
        ...
        break;
      default:
        abort();
    }

基于枚举值条件的 switch 语句如果是穷举的则不应有 `default`
情况。显式的 case 标签优于 `default`，即使这导致多个 case 标签
对应相同的代码。例如，而不是： >c

    case A:
      ...
    case B:
      ...
    case C:
      ...
    default:
      ...

你应该使用： >c

    case A:
      ...
    case B:
      ...
    case C:
      ...
    case D:
    case E:
    case F:
      ...

某些编译器不认识穷举的枚举 switch 语句为穷举的，这导致在
switch 语句的每个 case 中都有 return 语句但没有 catch-all
return 语句时产生编译器警告。要修复这些虚假错误，建议在
switch 语句之后使用 `UNREACHABLE` 来显式告诉编译器 switch
语句总是返回且其后的任何代码不可达。例如： >c

    enum { A, B, C } var;
    ...
    switch (var) {
      case A:
        return 1;
      case B:
        return 2;
      case C:
        return 3;
    }
    UNREACHABLE;

返回值 ~

不要不必要地用括号围绕 `return` 表达式。

仅在你也会在 `x = expr;` 中使用括号的地方在 `return expr;`
中使用括号。 >c

    return result;
    return (some_long_condition && another_condition);

    return (value);  // 你不会写 var = (value);
    return(result);  // return 不是函数！
