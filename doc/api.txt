Nvim API                                                           *API* *api*

Nvim 提供了一个强大的 API，可以被插件和外部进程通过 |RPC|、|Lua| 和
Vimscript (|eval-api|) 使用。

应用程序也可以嵌入 libnvim 来直接使用 C API。

                                      输入 |gO| 查看目录。

==============================================================================
API 使用                                                *api-rpc* *RPC* *rpc*

                                                        *msgpack-rpc*
RPC 是以编程方式控制 Nvim 的主要方式。Nvim 实现了 MessagePack-RPC 协议，
并有以下额外（非规范）约束：

1. 响应必须按请求的反序返回（类似于 "展开栈"）。
2. Nvim 按接收顺序处理所有消息（请求和通知）。

MessagePack-RPC 规范：
  https://github.com/msgpack-rpc/msgpack-rpc/blob/master/spec.md
  https://github.com/msgpack/msgpack/blob/0b8f5ac/spec.md

许多客户端使用 API：用户界面 (GUI)、远程插件、像 "nvr"
(https://github.com/mhinz/neovim-remote) 这样的脚本。甚至 Nvim 自身
也可以控制其他 Nvim 实例。API 客户端可以：

  - 调用任何 API 函数
  - 监听事件
  - 从 Nvim 接收远程调用

RPC API 就像是 Vim 的 "clientserver" 功能的更强大版本。

连接                                              *rpc-connecting*

参见 |channel-intro| 了解打开通道的各种方式。通道打开函数在选项字典中接受
`rpc` 键。RPC 通道也可以由其他进程通过连接到 Nvim 监听的 TCP/IP 套接字或
命名管道来打开。

Nvim 在 |startup| 时创建一个默认的 RPC 套接字，由 |v:servername| 给出。
要改为使用 TCP/IP 套接字启动，使用 |--listen| 加上 TCP 风格的地址： >
    nvim --listen 127.0.0.1:6666
可以使用 |serverstart()| 启动更多端点。

注意 localhost TCP 套接字通常不如命名管道安全，可能导致远程代码执行等
漏洞。

连接到套接字是程序员测试 API 的最简单方式，可以通过任何 msgpack-rpc
客户端库或完整的 |api-client| 来完成。这是一个在当前 Nvim 实例中打印
"hello world!" 的 Ruby 脚本：
>ruby
    #!/usr/bin/env ruby
    # Requires msgpack-rpc: gem install msgpack-rpc
    #
    # To run this script, use Nvim's built-in terminal emulator:
    #
    #   :term ./hello.rb
    #
    # Or from another shell by setting NVIM:
    # $ NVIM=[address] ./hello.rb

    require 'msgpack/rpc'
    require 'msgpack/rpc/transport/unix'

    nvim = MessagePack::RPC::Client.new(MessagePack::RPC::UNIXTransport.new, ENV['NVIM'])
    result = nvim.call(:nvim_command, 'echo "hello world!"')
<
更好的方式是使用带有 "pynvim" 包的 Python REPL，可以交互式地调用 API 函数：
>
    >>> from pynvim import attach
    >>> nvim = attach('socket', path='[address]')
    >>> nvim.command('echo "hello world!"')
<
你也可以通过 |jobstart()| 嵌入 Nvim，并使用 |rpcrequest()| 和
|rpcnotify()| 进行通信：
>vim
    let nvim = jobstart(['nvim', '--embed'], {'rpc': v:true})
    echo rpcrequest(nvim, 'nvim_eval', '"Hello " . "world!"')
    call jobstop(nvim)
<

API 定义                                                 *api-definitions*

                                                        *api-types*
Nvim C API 为所有函数参数定义了自定义类型。有些只是 C99 标准类型的
typedef，其他是 Nvim 定义的数据结构。

基本类型 ~
>
  API Type                              C type
  ------------------------------------------------------------------------
  Nil
  Boolean                               bool
  Integer (signed 64-bit integer)       int64_t
  Float (IEEE 754 double precision)     double
  String                                {char* data, size_t size} struct
  Array                                 kvec
  Dict (msgpack: map)                   kvec
  Object                                any of the above
<
  注意：
    - 空 Array 可作为有效的 Dictionary 参数。
    - 函数不能跨越 RPC 边界。但 API 函数（例如 |nvim_create_autocmd()|）
      可以为非 RPC 调用支持 Lua 函数参数。

特殊类型 (msgpack EXT) ~

  这些是作为独立 Object 子类型区分的整数 typedef。它们可以被视为不透明
  的整数，但彼此不兼容：Buffer 可以作为整数传递，但不能作为 Window 或
  Tabpage。

  EXT 对象数据是（整数）对象句柄。|api-metadata| `types` 键中给出的 EXT
  类型代码是稳定的：它们不会改变，因此是向前兼容的。
>
  EXT Type      C type                                  Data
  ------------------------------------------------------------------------
  Buffer        enum value kObjectTypeBuffer            |bufnr()|
  Window        enum value kObjectTypeWindow            |window-ID|
  Tabpage       enum value kObjectTypeTabpage           internal handle
<

                                                        *api-indexing*
大多数 API 使用基于 0 的索引，范围是端点排斥的。对于范围的末端，-1 表示
最后一行/列。

例外：以下 API 函数使用 "mark-like" 索引（行从 1 开始，列从 0 开始）：

- |nvim_get_mark()|
- |nvim_buf_get_mark()|
- |nvim_buf_set_mark()|
- |nvim_win_get_cursor()|
- |nvim_win_set_cursor()|

例外：以下 API 函数使用 |extmarks| 索引（基于 0 的索引，端点包含）：

- |nvim_buf_del_extmark()|
- |nvim_buf_get_extmark_by_id()|
- |nvim_buf_get_extmarks()|
- |nvim_buf_set_extmark()|

                                                        *api-fast* *schedule*
大多数 API 函数是延迟的：它们在主循环上排队（"调度"）并与正常输入按顺序
处理。如果编辑器以 "模态" 方式等待用户输入（例如 |input()| 提示），延迟
的请求将阻塞。
- 非延迟（快速）函数如 |nvim_get_mode()|、|nvim_input()| 或任何 Lua
  回调会立即执行（不在输入队列中排序）。
- Lua 代码可以使用 |vim.in_fast_event()| 检测快速上下文，在该上下文中
  可以与 Lua 状态交互，但不能与 "编辑器" 状态交互（|textlock|、选项、
  窗口布局等）。
- 要执行编辑器操作，Lua 代码必须通过 |vim.defer_fn()| 或
  |vim.schedule()| 调度，或等到 `vim.in_fast_event()` 返回 `false`。

API 元数据                                            *api-metadata*

Nvim C API 由构建系统自动暴露给 RPC，构建系统解析 src/nvim/api/* 中的
头文件并生成分发函数，将 RPC API 方法名映射到公共 C API 函数，转换/验证
参数和返回值。

Nvim 将其 API 元数据暴露为一个字典，包含以下项：

- version                 Nvim 版本，API 级别/兼容性
- version.api_level       API 版本整数 *api-level*
- version.api_compatible  API 向后兼容到此级别
- version.api_prerelease  将 API 声明为不稳定/未发布
                          `(version.api_prerelease && fn.since == version.api_level)`
- functions               API 函数签名，包含描述返回值和参数的 |api-types| 信息。
- ui_events               |UI| 事件签名
- ui_options              支持的 |ui-option|
- {fn}.since              函数 {fn} 引入时的 API 级别
- {fn}.deprecated_since   函数 {fn} 弃用时的 API 级别
- types                   Nvim 定义的自定义句柄类型
- error_types             API 函数可能返回的错误类型

关于 `functions` 映射：

  - 容器类型可能带有类型/大小约束装饰，例如
    ArrayOf(Buffer) 或 ArrayOf(Integer, 2)。
  - 被认为是操作 Nvim 特殊类型（msgpack EXT）实例的方法的函数有
    "method=true" 标志。接收者类型是第一个参数的类型。方法名以 `nvim_`
    加类型名为前缀，例如 `nvim_buf_get_lines` 是 Buffer 实例的
    `get_lines` 方法。|dev-api|
  - 全局函数有 "method=false" 标志，仅以 `nvim_` 为前缀，
    例如 `nvim_list_bufs`。

                                                        *api-mapping*
外部程序（客户端）可以使用元数据来发现 API，使用以下任一方法：

1. 连接到运行中的 Nvim 实例并通过 msgpack-RPC 调用 |nvim_get_api_info()|。
   这最适合用动态语言编写的客户端，可以在运行时定义函数。
2. 使用 |--api-info| 启动参数。适用于静态编译的客户端。
   示例（需要 Python "pyyaml" 和 "msgpack-python" 模块）： >
     nvim --api-info | python -c 'import msgpack, sys, yaml; yaml.dump(msgpack.unpackb(sys.stdin.buffer.read()), sys.stdout)'
3. 使用 |api_info()| 函数。 >vim
     :lua vim.print(vim.fn.api_info())
     " Example using filter() to exclude non-deprecated API functions:
     :new|put =map(filter(api_info().functions, '!has_key(v:val,''deprecated_since'')'), 'v:val.name')
<

API 契约                                                     *api-contract*

Nvim API 由函数和事件组成。

- 客户端调用函数，如 |api-global| 中描述的那些。
- 客户端可以订阅 |ui-events|、|api-buffer-updates| 等。
- API 函数名以 "nvim_" 为前缀。
- API 事件名以 "nvim_" 为前缀并以 "_event" 为后缀。

随着 Nvim 的发展，API 可能会按照此契约进行更改：

- 可能会添加新的函数和事件。
  - 任何此类扩展都是可选的：旧客户端可以忽略它们。
- 新函数在发布前可能会更改。客户端可以动态检查
  `api_prerelease`，|api-metadata|。
- 函数签名在发布后不会更改，除以下情况：
  - Map/list 参数/结果可能会被扩展（可能添加新字段）。
    - 此类新字段是可选的：旧客户端可以忽略它们。
    - 现有字段不会被删除。
  - 返回类型可能会从 void 变为非 void。旧客户端可以忽略新的返回值。
  - 可能会添加可选的 `opts` 参数。
  - 可能会在 `opts` 参数后添加可选参数。
- 事件参数不会被删除或重新排序（发布后）。
- 事件可能会被扩展：可能添加新参数。
- 弃用的函数在 Nvim 2.0 之前不会被删除。

"私有" 接口不在此契约覆盖范围内：

- 未文档化的（不在 :help 中）任何类型的函数或事件
- nvim__x（"双下划线"）函数

理念是 "无版本演进"，用 Rich Hickey 的话说：
- 放宽要求应该是兼容的变更。
- 加强承诺应该是兼容的变更。

缓冲区更新事件                                    *api-buffer-updates*

API 客户端可以 "附加" 到 Nvim 缓冲区以订阅缓冲区更新事件。
这类似于 |TextChanged| 但更强大和精细。

调用 |nvim_buf_attach()| 在通道上接收这些事件：

                                                        *nvim_buf_lines_event*
nvim_buf_lines_event[{buf}, {changedtick}, {firstline}, {lastline}, {linedata}, {more}]
    当 {firstline} 和 {lastline}（端点排斥，基于零索引）之间的缓冲区
    文本被更改为 {linedata} 列表中的新文本时触发。粒度是行级的，即如果
    在编辑器中更改了单个字符，也会发送整行。

    当 {changedtick} 为 |v:null| 时，表示屏幕行（显示）发生了变化，
    但缓冲区内容没有变化。{linedata} 包含已更改的屏幕行。这在
    'inccommand' 显示缓冲区预览时发生。

    Parameters: ~
      • {buf}         (`integer`) 缓冲区 id
      • {changedtick} (`integer`) |b:changedtick| 的值。如果你向 Nvim
                      发回 API 命令，可以检查 |b:changedtick| 作为请求
                      的一部分，以确保没有发生其他更改。
      • {firstline}   (`integer`) 被替换的第一行。
                      基于零索引：如果替换了第 1 行，{firstline}
                      将是零而不是一。始终小于或等于替换前缓冲区
                      中的行数。
      • {lastline}    (`integer`) 未被替换的第一行（即范围
                      {firstline}, {lastline} 是端点排斥的）。
                      基于零索引：如果替换了第 2 到第 5 行，
                      这将是 5 而不是 6。始终小于或等于替换前
                      缓冲区中的行数。如果事件是附加后初始更新
                      的一部分，将为 -1。
      • {linedata}    (`string[]`) 新缓冲区行的内容。换行符
                      被省略；空行作为空字符串发送。
      • {more}        (`boolean`) 对于 "多部分" 变更通知为 true：
                      当前变更被分块为多个
                      |nvim_buf_lines_event| 通知（例如因为
                      太大）。

nvim_buf_changedtick_event[{buf}, {changedtick}]  *nvim_buf_changedtick_event*
    当 |b:changedtick| 增加但没有文本更改时触发。与撤销/重做相关。

    Parameters: ~
      • {buf}         (`integer`) 缓冲区 id
      • {changedtick} (`integer`) |b:changedtick| 的新值。

nvim_buf_detach_event[{buf}]                           *nvim_buf_detach_event*
    当缓冲区被分离（即禁用更新）时触发。由 |nvim_buf_detach()| 显式触发，
    或在以下情况下隐式触发：
    - 缓冲区被 |abandon| 且 'hidden' 未设置。
    - 缓冲区被重新加载，例如使用 |:edit| 或由 |:checktime| 或
      'autoread' 触发的外部变更。
    - 通常：当缓冲区内容从内存中卸载时。

    Parameters: ~
      • {buf}         (`integer`) 缓冲区 id


示例 ~

使用 send_buffer=true 在空缓冲区上调用 |nvim_buf_attach()|，发出： >
    nvim_buf_lines_event[{buf}, {changedtick}, 0, -1, [""], v:false]

用户向缓冲区添加两行，发出： >
    nvim_buf_lines_event[{buf}, {changedtick}, 0, 0, ["line1", "line2"], v:false]

用户移动到包含文本 "Hello world" 的行并插入 "!"，发出： >
    nvim_buf_lines_event[{buf}, {changedtick}, {linenr}, {linenr} + 1,
                         ["Hello world!"], v:false]

用户移动到第 3 行并使用 "20dd" 删除 20 行，发出： >
    nvim_buf_lines_event[{buf}, {changedtick}, 2, 22, [], v:false]

用户使用 |linewise-visual| 模式选择第 3-5 行，然后按 "p" 粘贴 6 行的块，
发出： >
    nvim_buf_lines_event[{buf}, {changedtick}, 2, 5,
      ['pasted line 1', 'pasted line 2', 'pasted line 3', 'pasted line 4',
       'pasted line 5', 'pasted line 6'],
      v:false
    ]

用户使用 ":edit" 重新加载缓冲区，发出： >
    nvim_buf_detach_event[{buf}]
<

LUA ~
                                                        *api-buffer-updates-lua*
进程内插件可以通过 Lua 回调接收缓冲区更新。这些回调在各种上下文中频繁
调用；|textlock| 阻止更改缓冲区内容和窗口布局（此类操作必须被
|schedule|）。允许移动光标，但之后会恢复。

|nvim_buf_attach()| 将为回调接受关键字参数。"on_lines" 将接收参数
("lines", {buf}, {changedtick}, {firstline}, {lastline},
{new_lastline}, {old_byte_size} [, {old_utf32_size}, {old_utf16_size}])。
与远程通道事件不同，文本内容不会传递。新文本可以在回调内部通过以下方式
访问 >lua

    vim.api.nvim_buf_get_lines(buf, firstline, new_lastline, true)
<
{old_byte_size} 是被替换区域 {firstline} 到 {lastline} 的总字节大小，
包括 {lastline} 后的最终换行符。如果在 |nvim_buf_attach()| 关键字参数中
将 `utf_sizes` 设置为 true，则删除区域的 UTF-32 和 UTF-16 大小也会作为
额外参数 {old_utf32_size} 和 {old_utf16_size} 传递。

"on_changedtick" 在 |b:changedtick| 增加但没有文本更改时调用。接收的
参数为 ("changedtick", {buf}, {changedtick})。

                                                        *api-lua-detach*
进程内 Lua 回调可以通过返回 `true` 来分离。这将分离同一 |nvim_buf_attach()|
调用附加的所有回调。

缓冲区高亮                                            *api-highlights*

Nvim 允许插件向缓冲区添加基于位置的高亮。这类似于 |matchaddpos()| 但有
一些关键区别。添加的高亮与缓冲区关联，并适应行的插入和删除，类似于标记。
也可以将一组高亮作为一个组来管理，一次性删除或替换全部。

预期的使用场景是 linter 或语义高亮插件，它们监视缓冲区的变更，并在后台
计算缓冲区的高亮。另一个使用场景是在仅追加缓冲区中显示输出的插件，
希望为输出添加高亮。高亮数据不能在写入和加载缓冲区到文件时保留，
也不能在撤销/重做循环中保留。

高亮使用 |nvim_buf_set_extmark()| 函数注册，它将高亮添加为 |extmarks|。
如果需要在添加后跟踪或操作高亮，可以使用返回的 |extmark| id。 >lua
  -- create the highlight through an extmark
  extid = vim.api.nvim_buf_set_extmark(buf, ns_id, line, col_start, {end_col = col_end, hl_group = hl_group})

  -- example: modify the extmark's highlight group
  vim.api.nvim_buf_set_extmark(buf, ns_id, line, col_start, {end_col = col_end, hl_group = NEW_HL_GROUP, id = extid})

  -- example: change the highlight's position
  vim.api.nvim_buf_set_extmark(buf, ns_id, NEW_LINE, col_start, {end_col = col_end, hl_group = NEW_HL_GROUP, id = extid})
<

另见 |vim.hl.range()|。

浮动窗口                                *api-floatwin* *floating-windows*

浮动窗口（"浮窗"）显示在普通窗口之上。这对于实现简单的部件很有用，
例如显示在光标旁边的工具提示。浮窗是完全功能的窗口，支持用户编辑、
常见的 |api-window| 调用和大多数窗口选项（'statusline' 除外）。

创建浮动窗口的两种方式：
- |nvim_open_win()| 创建新窗口（需要缓冲区，参见 |nvim_create_buf()|）
- |nvim_win_set_config()| 将普通窗口重新配置为浮窗

使用 |nvim_win_close()| 或 |:close| 等命令关闭它。

要检查窗口是否是浮动的，检查其配置中的 `relative` 选项是否非空： >lua

    if vim.api.nvim_win_get_config(window_id).relative ~= '' then
      -- window with this window_id is floating
    end
<

缓冲区文本可以通过典型机制（语法高亮、|api-highlights|）进行高亮。
|hl-NormalFloat| 组高亮普通文本；'winhighlight' 可以像往常一样用于
本地覆盖组。浮窗从当前窗口继承选项；在 |nvim_open_win()| 中指定
`style=minimal` 以禁用各种视觉功能，如 'number' 列。

浮动窗口特有的其他高亮组：
- |hl-FloatBorder| 用于窗口的边框
- |hl-FloatTitle| 用于窗口的标题
- |hl-FloatFooter| 用于窗口的页脚

目前，浮动窗口不支持某些部件，如滚动条。

|:mksession| 的输出不包括恢复浮动窗口的命令。

示例：创建一个带有临时缓冲区的浮窗： >vim

    let buf = nvim_create_buf(v:false, v:true)
    call nvim_buf_set_lines(buf, 0, -1, v:true, ["test", "text"])
    let opts = {'relative': 'cursor', 'width': 10, 'height': 2, 'col': 0,
        \ 'row': 1, 'anchor': 'NW', 'style': 'minimal'}
    let win = nvim_open_win(buf, 0, opts)
    " optional: change highlight, otherwise Pmenu is used
    call nvim_set_option_value('winhl', 'Normal:MyHighlight', {'win': win})
<

==============================================================================
扩展标记                       *api-extended-marks* *extmarks* *extmark*

扩展标记 (extmarks) 表示跟踪缓冲区中文本变更的缓冲区注释。它们可以表示
光标、折叠、拼写错误的单词，以及任何需要在缓冲区中随时间跟踪逻辑位置的
内容。|api-indexing|

Extmark 位置的工作方式类似于 "竖条" 光标：它存在于字符之间。因此，一行上
的最大 extmark 索引比字符索引多 1： >

     f o o b a r      行内容
     0 1 2 3 4 5      字符位置（基于 0）
    0 1 2 3 4 5 6     extmark 位置（基于 0）

Extmark 具有 "前向引力"：如果你将光标直接放在 extmark 位置上并输入一些
文本，extmark 会向前迁移。 >

     f o o|b a r      行（| = 光标）
          3           extmark

     f o o z|b a r    行（| = 光标）
            4         extmark（输入 "z" 后）

如果 extmark 在行的最后一个索引上，你在该点输入换行符，extmark 将相应地
迁移到下一行： >

     f o o z b a r|   行（| = 光标）
                  7   extmark

     f o o z b a r    第一行
                      extmarks（没有）
     |                第二行（| = 光标）
     0                extmark（输入 <CR> 后）


示例：

让我们在第一行（row=0）第三列（column=2）设置一个 extmark。
|api-indexing| 传递 id=0 创建一个新标记并返回 id： >

      01 2345678
    0 ex|ample..
        ^ extmark 位置
<
>vim
    let g:mark_ns = nvim_create_namespace('myplugin')
    let g:mark_id = nvim_buf_set_extmark(0, g:mark_ns, 0, 2, {})
<
我们可以通过 id 获取标记： >vim

    echo nvim_buf_get_extmark_by_id(0, g:mark_ns, g:mark_id, {})
    " => [0, 2]

我们可以通过 |namespace|（或通过范围）获取缓冲区中的所有标记： >vim

    echo nvim_buf_get_extmarks(0, g:mark_ns, 0, -1, {})
    " => [[1, 0, 2]]

删除所有周围文本不会删除 extmark！要删除 extmarks 使用
|nvim_buf_del_extmark()|。在我们的示例中删除 "x"： >

      0 12345678
    0 e|ample..
       ^ extmark 位置
<
>vim
    echo nvim_buf_get_extmark_by_id(0, g:mark_ns, g:mark_id, {})
    " => [0, 1]
<
    注意：Extmark "引力" 决定了它在文本编辑后如何移动。
          参见 |nvim_buf_set_extmark()|

命名空间允许任何插件仅管理自己的 extmarks，忽略其他插件创建的。

由编辑更改的 Extmark 位置将在撤销/重做时恢复。创建和删除 extmarks
不是缓冲区更改，因此不会为 extmark 更改创建新的撤销状态。

                       |Progress| 事件来执行取消。

    执行错误时：不会失败，但更新 v:errmsg。

    Note: ~
      • |keycodes| 如 <CR> 会被转换，所以 "<" 是特殊的。要输入字面
        "<"，发送 <LT>。
      • 对于鼠标事件使用 |nvim_input_mouse()|。伪键形式
        `<LeftMouse><col,row>` 从 |api-level| 6 起已弃用。

    Attributes: ~
        |api-fast|
        Since: 0.1.0

    Parameters: ~
      • {keys}  (`string`) 要键入的字符

    Return: ~
        (`integer`) 实际写入的字节数（如果缓冲区满了可能少于请求的）。

nvim_input_mouse({button}, {action}, {modifier}, {grid}, {row}, {col})
    从 GUI 发送鼠标事件。

    非阻塞：不等待任何结果，而是将事件排队以便事件循环尽快处理。

    Note: ~
      • 目前不支持通过在循环中多次调用来 "脚本化" 多个鼠标事件：
        中间鼠标位置将被忽略。应该用于在 GUI 中实现实时鼠标输入。
        |nvim_input()| 的弃用伪键形式 (`<LeftMouse><col,row>`) 有
        相同的限制。

    Attributes: ~
        |api-fast|
        Since: 0.4.0

    Parameters: ~
      • {button}    (`string`) 鼠标按钮："left"、"right"、"middle"、
                    "wheel"、"move"、"x1"、"x2" 之一。
      • {action}    (`string`) 对于普通按钮，"press"、"drag"、
                    "release" 之一。对于滚轮，"up"、"down"、"left"、
                    "right" 之一。"move" 时忽略。
      • {modifier}  (`string`) 修饰符字符串，每个修饰符用单个字符表示。
                    使用与按键相同的说明符，除了 "-" 分隔符是可选的，
                    所以 "C-A-"、"c-a" 和 "CA" 都可以用来指定
                    Ctrl+Alt+click。
      • {grid}      (`integer`) 网格编号（由 |ui-multigrid| 客户端使用），
                    或 0 让 Nvim 决定窗口定位。更多信息参见
                    |dev-ui-multigrid|
      • {row}       (`integer`) 鼠标行位置（基于零，如重绘事件）
      • {col}       (`integer`) 鼠标列位置（基于零，如重绘事件）

nvim_open_term({buffer}, {opts})                            *nvim_open_term()*
    在缓冲区中打开终端实例

    默认（且目前唯一的选项）终端不会连接到外部进程。相反，在通道上发送
    的输入将直接由终端回显。这对于显示作为 RPC 消息一部分返回的 ANSI
    终端序列或类似内容很有用。

    注意：要直接以正确的大小初始化终端，在调用此函数之前先在已配置的
    窗口中显示缓冲区。例如，对于浮动显示，先使用 |nvim_create_buf()|
    创建空缓冲区，然后使用 |nvim_open_win()| 显示它，然后调用此函数。
    然后可以立即调用 |nvim_chan_send()| 在具有预期大小的虚拟终端中
    处理序列。

    Example: 此 `TermHl` 命令可用于显示和高亮原始 ANSI 终端码，
    这样你可以将 Nvim 用作 "回滚分页器"（用于像 kitty 这样的终端）：
                     *ansi-colorize* *terminal-scrollback-pager* >lua
        vim.api.nvim_create_user_command('TermHl', function()
          vim.api.nvim_open_term(0, {})
        end, { desc = 'Highlights ANSI termcodes in curbuf' })
<

    Attributes: ~
        当 |textlock| 活动时不允许
        Since: 0.5.0

    Parameters: ~
      • {buffer}  (`integer`) 要使用的缓冲区。缓冲区内容（如果有）
                  将写入 PTY。
      • {opts}    (`vim.api.keyset.open_term`) 可选参数。
                  • on_input: 输入发送时的 Lua 回调，即终端模式中的
                    按键。注意：按键按原始方式发送，如同发送到 pty
                    主端。例如，回车作为 "\r" 而非 "\n" 发送。
                    |textlock| 适用。但可以在回调中直接调用
                    |nvim_chan_send()|。`["input", term, bufnr, data]`
                  • force_crlf: (boolean, 默认 true) 将 "\n" 转换为
                    "\r\n"。

    Return: ~
        (`integer`) 通道 id，错误时为 0

nvim_paste({data}, {crlf}, {phase})                             *nvim_paste()*
    在光标处粘贴（在任何模式下），并设置 "redo" 使点 (|.|) 重复输入。
    UI 调用此来实现 "粘贴"，但也旨在供脚本使用，以输入大的、可点重复
    的文本块（相对于 |nvim_input()| 受映射/事件影响，因此慢得多）。

    调用 |vim.paste()| 处理程序，它适当地处理每种模式。

    错误（'nomodifiable'、`vim.paste()` 失败等）反映在 `err` 中但不影响
    返回值（由 `vim.paste()` 严格决定）。错误或取消时，后续调用被忽略
    （"排空"）直到启动下一次粘贴（阶段 1 或 -1）。

    在映射和脚本中插入多行文本很有用。Example: >lua
        vim.keymap.set('n', 'x', function()
          vim.api.nvim_paste([[
            line1
            line2
            line3
          ]], false, -1)
        end, { buf = 0 })
<

    Attributes: ~
        当 |textlock| 活动时不允许
        Since: 0.4.0

    Parameters: ~
      • {data}   (`string`) 多行输入。行在 LF ("\n") 处断开。
                 可以是二进制的（包含 NUL 字节）。
      • {crlf}   (`boolean`) 也在 CR 和 CRLF 处断行。
      • {phase}  (`integer`) -1：在单次调用中粘贴（即不流式传输）。
                 要 "流式" 粘贴，依次调用 `nvim_paste` 使用这些
                 `phase` 值：
                 • 1：开始粘贴（恰好一次）
                 • 2：继续粘贴（零次或多次）
                 • 3：结束粘贴（恰好一次）

    Return: ~
        (`boolean`)
        • true：客户端可以继续粘贴。
        • false：客户端应取消粘贴。

nvim_put({lines}, {type}, {after}, {follow})                      *nvim_put()*
    在光标处放置文本，在任何模式下。对于可点重复的输入，使用
    |nvim_paste()|。

    比较 |:put| 和 |p|，它们总是按行方式。

    Attributes: ~
        当 |textlock| 活动时不允许
        Since: 0.4.0

    Parameters: ~
      • {lines}   (`string[]`) |readfile()| 风格的行列表。
                  |channel-lines|
      • {type}    (`string`) 编辑行为：任何 |getregtype()| 结果，或：
                  • "b" |blockwise-visual| 模式（可包含宽度，例如 "b3"）
                  • "c" |charwise| 模式

                  • "" 根据内容猜测，参见 |setreg()|
      • {after}   (`boolean`) 如果为 true 在光标后插入（如 |p|），

                                                      *nvim_set_client_info()*
nvim_set_client_info({name}, {version}, {type}, {methods}, {attributes})
    自我标识客户端，并在通道上设置可选标志。
    定义 |nvim_get_chan_info()| 返回的 `client` 对象。

    客户端应在连接后立即调用此函数，以提供调试和编排的提示。
    （注意：有总比没有好！字段是可选的，但至少设置 `name`。）

    可以多次调用；调用者应在适当时合并旧信息。
    例如：库首先标识通道，然后使用该库的插件稍后标识自己。

    Attributes: ~
        仅 |RPC|
        Since: 0.3.0

    Parameters: ~
      • {name}        (`string`) 客户端短名。设置
                      |nvim_get_chan_info()| 的 `client.name` 字段。
      • {version}     (`table<string,any>`) 描述版本的字典，有以下
                      （可选）键：
                      • "major" 主版本号（如果未设置默认为 0，
                        表示尚未发布）
                      • "minor" 次版本号
                      • "patch" 补丁号
                      • "prerelease" 描述预发布的字符串，如
                        "dev" 或 "beta1"
                      • "commit" 提交的哈希或类似标识符
      • {type}        (`string`) 必须是以下值之一。客户端库应默认为
                      "remote"，除非被用户覆盖。
                      • "remote" 连接的远程客户端 "Nvim 风味"
                        MessagePack-RPC（响应必须按请求的反序）。
                        |msgpack-rpc|
                      • "msgpack-rpc" 通过完全符合 MessagePack-RPC
                        协议连接到 Nvim 的远程客户端。
                      • "ui" GUI 前端
                      • "embedder" 使用 Nvim 作为组件的应用程序
                        （例如实现 vim 模式的 IDE/编辑器）。
                      • "host" 插件宿主，通常由 nvim 启动
                      • "plugin" 单个插件，由 nvim 启动
      • {methods}     (`table<string,any>`) 客户端中的内置方法。
                      对于宿主，不包括稍后发现的插件方法。键应是方法
                      名称，值是有以下（可选）键的字典（Nvim 未来版本
                      可能添加更多键，因此未知键被忽略。客户端必须
                      仅使用此版本或更高版本 Nvim 中定义的键）：
                      • "async" 如果为 true，作为通知发送。如果为
                        false 或未指定，使用阻塞请求
                      • "nargs" 参数数量。可以是单个整数或两个整数
                        的数组，最小和最大（包含）。
      • {attributes}  (`table<string,any>`) 任意 string:string 的
                      非正式客户端属性映射。建议的键：
                      • "pid"：进程 id。
                      • "website"：客户端主页 URL（例如 GitHub 仓库）
                      • "license"：许可证描述（"Apache 2"、"GPLv3"、
                        "MIT" 等）
                      • "logo"：图像的 URI 或路径，最好是小 logo 或
                        图标。推荐 .png 或 .svg 格式。
